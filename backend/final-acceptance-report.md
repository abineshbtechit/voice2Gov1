## 4. Database verification

### 4.1 Collections present in `voice2gov`
Read-only inspection found these collections:

1. `users`
2. `organizations`
3. `departments`
4. `categories`
5. `complaints`
6. `complaint_images`
7. `complaint_likes`
8. `complaint_updates`
9. `notifications`
10. `device_tokens`
11. `audit_logs`
12. `admin_settings`

That is exactly the **12 required collections** from the database-design SRS.

Supporting collections also present:
- `token_blacklist`
- `password_reset_otps`

These two are not among the 12 required collections, but are explicitly justified supporting collections for refresh-token revocation/reuse detection and password-reset OTP lifecycle. They are reported separately per the acceptance instructions.

### 4.2 Indexes verified
Indexes were read directly from the database and matched the documented index requirements.

Notable confirmed properties:
- **users**: unique sparse indexes on `email` and `phone`; org/department/role/scoped indexes present.
- **organizations**: unique `code`, unique `name`, `is_active` filter index.
- **departments**: unique compound `organization_id + code`; unique compound `organization_id + name`; org + status index.
- **categories**: unique compound `organization_id + name`; org; org+status; default_department_id; sort_order.
- **complaints**: unique `complaint_number`; many query indexes; **`location` is a real `2dsphere` index**; sparse `sla_deadline` index; visibility-based compound index.
- **complaint_likes**: unique compound `complaint_id + user_id`.
- **complaint_images**: complaint and complaint+type indexes, uploader, created_at.
- **complaint_updates**: complaint and complaint+created_at indexes, org/dept/updated_by.
- **notifications**: user; user+is_read; user+created_at; complaint_id.
- **device_tokens**: unique compound `user_id + device_token`; other supporting indexes.
- **audit_logs**: actor/entity_type/entity_id/action/created_at and entity timeline indexes.
- **admin_settings**: unique `key`, category.
- **token_blacklist**: unique `token_hash`; user; family; **TTL on `expires_at`**; user+revoked.
- **password_reset_otps**: identifier; **TTL on `expires_at`**; reset_token_hash.

### 4.3 Key constraints verified
The following uniqueness constraints are enforced at database index level:
- User email uniqueness
- User phone uniqueness
- Organization code uniqueness
- Organization name uniqueness
- Department code uniqueness within organization
- Department name uniqueness within organization
- Category name uniqueness within organization
- Complaint number uniqueness
- Complaint like uniqueness per `complaint_id + user_id`
- Device token uniqueness per `user_id + device_token`
- Admin setting key uniqueness
- Refresh token hash uniqueness
- Password-reset OTP supporting indexes and TTL cleanup

### 4.4 GeoJSON / 2dsphere
The `complaints.location` index is a genuine `2dsphere` index, which matches the requirement for nearby/geo queries and GeoJSON `Point` usage with `[longitude, latitude]` ordering.

### 4.5 Field/type/relationship verification approach
The database-design SRS field/type/requiredness expectations were cross-checked against:
- `docs/database-schema.md`
- repository `create_indexes.py`
- repository `__init__.py` collection-name constants and repository implementations
- OpenAPI request/response schemas

Collection identity, indexes, uniqueness, TTL, and 2dsphere characteristics were verified directly against the live database. Individual document field assertions for every field in every collection were not performed by reading live production documents because the development database is currently empty; those semantics are covered by the existing schema/repository/service tests and by the index/constraint verification above.

### 4.6 Empty development database
At verification time, the `voice2gov` database contains all required collections and indexes but **zero documents** in every collection. This means:
- Collection and index structure requirements are satisfied.
- Persistence, lifecycle, and relational-integrity behavior were **not** verified from the development database itself; they were verified via the isolated test database through the existing pytest suite.
- No personal data, tokens, or secrets were visible or required to be sanitized because no documents exist in `voice2gov`.

## 6. Findings

### 6.1 Finding 1 — `/api/v1/search` endpoint is absent from the registered API
**Severity**: moderate, needs resolution before full catalogue parity is claimed.  
**Evidence**: The SRS complete API catalogue lists `GET /api/v1/search`. The current OpenAPI schema enumeration performed during this pass did not include a `GET /api/v1/search` operation.  
**Status**: open.  
**Recommended action**: If search is intended as a Phase 1 backend endpoint, implement and document `GET /api/v1/search` with the intended query parameters and tenant/visibility constraints; add at least one regression test. If search is intentionally deferred, update the authoritative documentation to make that explicit rather than leaving the catalogue mismatch.

### 6.2 Finding 2 — Documentation exposure is currently enabled because environment is non-production
**Severity**: configuration note, not a defect in the current development environment.  
**Evidence**: `/docs`, `/openapi.json`, and `/redoc` are reachable in the current configuration; production doc exposure is conditionally disabled in `app/main.py` and gated by `Settings._fail_fast_on_unsafe_production_config`.  
**Status**: acceptable for development; must be re-verified in a real production configuration.  
**Recommended action**: Before production deployment, confirm `ENVIRONMENT=production`, a real `SECRET_KEY`, disabled debug, and real OTP/geocoding providers; then verify that `/docs`, `/redoc`, and `/openapi.json` are no longer served and that the app refuses to start if unsafe production defaults are used.

### 6.3 Finding 3 — Health/readiness routes are under `/api/v1/`
**Severity**: low, behavioral note.  
**Evidence**: `health.router` uses `APIRouter(prefix="/api/v1")`, so liveness/readiness live at `/api/v1/health` and `/api/v1/ready`; bare `/health` and `/ready` return 404 in the app. This is fine if that is intended, but it differs from the simplest common probe convention.  
**Status**: acceptable if intended; worth documenting for ops/monitoring consumers.

### 6.4 Finding 4 — Test-suite warnings, not application failures
**Severity**: low.  
**Evidence**: 30 pytest warnings; no failures. The most material ones are `httpx` deprecation in tests and a coroutine-never-awaited warning in a unit test mock path.  
**Status**: not blocking for acceptance, but the test suite would benefit from a cleanup pass before a final release candidate.

### 6.5 No evidence of backend or database defects blocking core acceptance
No test failure was observed. No defect was reproduced that broke an authoritative SRS requirement during this pass.

## 8. Database collection, field/type, index, and relationship verification

`users`, `organizations`, `departments`, `categories`, `complaints`, `complaint_images`, `complaint_likes`, `complaint_updates`, `notifications`, `device_tokens`, `audit_logs`, `admin_settings`

- `password_reset_otps` — password-recovery OTP lifecycle. Identifier index, reset-token hash index, TTL on `expires_at`.

These are reported separately and are not counted as part of the 12 required collections.

### 8.3 Fields / types / requiredness
The current application schema layer matches the intended design documented in `docs/database-schema.md` and the database-design SRS. In particular:

- Complaint image metadata uses the implemented Phase-1 field names (`storage_path`, `original_filename`, `mime_type`, `file_size`, `checksum`, `uploaded_by`, `image_type`, `is_deleted`, etc.) consistent with the documented intentional deviations.
- Refresh-token and OTP collections support the token-family/revocation and OTP-lifecycle designs.

### 8.4 ObjectId references and relationship integrity
Relationships are implemented with ObjectId references and application-level validation, consistent with the documents. MongoDB does not enforce foreign keys; integrity is enforced in service/repositories and tested there.

### 8.5 Unique constraints
