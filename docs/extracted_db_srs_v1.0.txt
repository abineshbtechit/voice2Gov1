1. Introduction
This document defines the database-specific requirements for Voice2Gov. It is derived from the existing Voice2Gov
Software Requirements Specification and isolates the MongoDB persistence design. The database supports citizen
complaint registration, organization routing, department assignment, community likes, complaint progress tracking,
notifications, administration, analytics, and auditability.
2. Database Objectives
 Store authenticated users and role information securely.
 Store organizations, departments, and complaint categories.
 Store complete civic complaint records including location and priority information.
 Store complaint photographs and evidence metadata.
 Prevent duplicate likes from the same user.
 Preserve complaint status and progress history.
 Deliver and track in-app and push notification data.
 Record administrative and organization actions through audit logs.
 Support geospatial complaint queries using MongoDB 2dsphere indexing.
 Support indexed, paginated access for large complaint and notification datasets.
3. Database Scope
The database scope includes the 12 required MongoDB collections: users, organizations, departments, categories,
complaints, complaint_images, complaint_likes, complaint_updates, notifications, device_tokens, audit_logs, and
admin_settings. The original SRS identifies these collections as the recommended MongoDB design.

5. Database Architecture
Voice2Gov uses a document-oriented MongoDB database accessed by the Python FastAPI backend. Relationships
are represented primarily through ObjectId references rather than relational SQL foreign keys. Complaint locations use
GeoJSON Point format, and large image binaries should be kept in secure object storage or GridFS while MongoDB
stores references and metadata. ■filecite■turn0file0■L255-L268■ ■filecite■turn0file0■L860-L862■

9. Complaint Status Lifecycle
 SUBMITTED — complaint successfully registered.
 ONGOING — organization has acknowledged the complaint and work has started.
 PROCESSING — complaint is actively being investigated or resolved.
 COMPLETED — work has been completed and the complaint is resolved.
 REJECTED — complaint rejected with a reason.
 DUPLICATE — complaint identified as a duplicate.
 CLOSED — complaint lifecycle administratively closed.
 Primary flow: SUBMITTED → ONGOING → PROCESSING → COMPLETED.
The original SRS requires backend validation to prevent invalid transitions such as COMPLETED → SUBMITTED.
■filecite■turn0file0■L304-L326■
10. Complaint Priority Data Model
The priority model combines community engagement, severity, complaint age, and organization-configured priority.
The original SRS specifies configurable weighting so the formula can evolve without changing the mobile application.
■filecite■turn0file0■L289-L302■
Recommended stored components are priority_score, community_engagement_score, severity_score and age_score.
Organization-specific weights can be maintained in admin_settings or organization configuration.

12. Data Integrity and Constraints
 User email must be unique.
 Organization code must be unique.
 Complaint number must be unique.
 Complaint likes must use a unique compound index on complaint_id + user_id.
 Complaint status must be restricted to the defined lifecycle values.
 Invalid status transitions must be rejected by the backend.
 Organization users must be restricted to their own organization records.
 Required ObjectId references must be validated before insertion or update.
 Coordinates must follow [longitude, latitude] GeoJSON ordering.
 Timestamps should be stored consistently in UTC.
13. File and Image Storage
Complaint photographs, progress evidence, completion evidence, and profile images should be represented in
MongoDB by metadata and secure storage references. The original SRS recommends secure object storage or
GridFS. ■filecite■turn0file0■L246-L249■ ■filecite■turn0file0■L860-L862■
14. Security Requirements
 JWT access and refresh token architecture.
 Argon2 or bcrypt password hashing.
 Role-based authorization.

 Organization-level tenant isolation.
 Pydantic/FastAPI input validation.

15. Database Query Requirements
 Citizen complaints by user_id with created_at sorting.
 Organization queue by organization_id.
 Department queue by department_id.
 Public community feed with pagination.
 Nearby complaints using the 2dsphere index.
 Complaint timeline by complaint_id ordered by created_at.
 Unread notifications by user_id and is_read.
 High-priority complaints ordered by priority_score.
16. Data Flow
Complaint creation: users → categories → organizations/departments → complaints → complaint_images →
complaint_updates → notifications → audit_logs.
Community engagement: users → complaints → complaint_likes → complaint priority.
Organization processing: complaints → users/departments → complaint_updates → complaint_images → notifications
→ audit_logs.
Push notifications: users → device_tokens → notifications.
17. Backup, Reliability and Performance
 Automated MongoDB backup and recovery procedures.
 Pagination for large lists.
 Indexes for common queries.
 Aggregation pipelines for dashboard analytics.
 Asynchronous FastAPI operations where appropriate.
 Asynchronous processing for heavy image and notification work.
 Retries for transient storage and notification failures.
 Meaningful database/API error handling.
 Target normal API response time below 500 ms where practical.
 Target normal feed loading below 2 seconds under normal network conditions.
These performance targets align with the original SRS. ■filecite■turn0file0■L864-L879■

18. Database Acceptance Criteria
 All 12 required MongoDB collections are created.
 Each collection contains the defined fields and types.
 ObjectId references are used consistently.
 Complaints support user, organization, department, category, location, status, priority and assignment.
 Complaint images use metadata and secure storage references.
 Duplicate likes are prevented.
 Status transitions are validated.
 GeoJSON locations support a 2dsphere index.
 Complaint progress history is preserved.
 Notifications and device tokens support notification delivery.
 Administrative actions are auditable.
 Organization tenant isolation is enforced.
 Required indexes are created and tested.
 Citizen, organization and admin portal queries are supported.
 Backup and recovery procedures are defined before production deployment.
